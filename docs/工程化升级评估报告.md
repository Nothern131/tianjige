## 一、当前架构全景

### 1.1 整体架构

```
用户界面 (index.html / architecture.html)
    │
    ├── JS前端（主力计算层）
    │   ├── engine-registry.js      ← 引擎注册中心（统一调度）
    │   ├── bazi-engine.js          ← 八字排盘（纯前端实现）
    │   ├── ziwei-engine.js         ← 紫微斗数（纯前端实现）
    │   ├── qimen-engine.js         ← 奇门遁甲（纯前端实现）
    │   ├── liuyao-engine.js        ← 六爻（纯前端实现）
    │   ├── meihua-engine.js        ← 梅花易数（纯前端实现）
    │   ├── taiyi-engine.js         ← 太乙神数（纯前端实现）
    │   ├── zhuge-engine.js         ← 诸葛神数（纯前端实现）
    │   ├── zhougong-engine.js      ← 周公解梦（纯前端实现）
    │   ├── daliuren-engine.js      ← 大六壬（纯前端实现）
    │   ├── fengshui-engine.js      ← 风水格局（纯前端实现）
    │   ├── masters-engine.js       ← 34位大师蒸馏（纯前端）
    │   ├── composite-engine.js     ← 多术合参（纯前端）
    │   ├── domain-analysis.js      ← 事域分析（纯前端）
    │   └── components/             ← 10个UI组件
    │
    └── Python后端（薄封装层 + 部分独立计算）
        ├── app.py                  ← FastAPI入口（44行）
        ├── api/bazi_api.py         ← 单体API路由（532行，13个端点）
        └── core/
            ├── constants.py        ← 核心常量（1100+行）
            ├── calendar.py         ← 农历日历（370行）
            ├── liuyao.py           ← 六爻（类实现）
            ├── meihua.py           ← 梅花易数（类实现）
            ├── qimen.py            ← 奇门遁甲（类实现）
            └── taiyi.py            ← 太乙神数（类实现）
```

### 1.2 数据流

```
用户输入 → [JS前端] engine-registry.js 调度
              │
              ├── 八字/紫微 → 前端 bazi-engine.js / ziwei-engine.js 直接排盘
              ├── 六爻/梅花/奇门/太乙 → 前端 JS引擎 或 后端 API
              ├── 大师分析 → masters-engine.js 调用模板
              └── 多术合参 → composite-engine.js 加权融合
              
              ↓
         [可选] FastAPI → bazi_api.py → core/*.py 计算 → 返回
```

**关键发现**：前端是主力计算层，后端是可选辅助。八字排盘在前端(bazi-engine.js)和后端(core/calendar.py)各有一套独立实现。

## 二、逐模块分析

### 2.1 Python后端结构

| 文件 | 行数 | 职责 | 质量评估 |
|------|------|------|----------|
| `app.py` | 44 | FastAPI入口，挂载静态文件+路由 | 简洁，但仅注册了bazi路由 |
| `api/bazi_api.py` | 532 | 13个端点 + 所有分析函数 + 大师数据 | **严重单体**，需拆分 |
| `core/constants.py` | 1100+ | 天干地支、五行、神煞、卦象等所有常量 | 数据完整，但过大 |
| `core/calendar.py` | 370 | 农历日历（含lunar-python降级） | 有降级设计，但混合了四柱+大运 |
| `core/liuyao.py` | ~300 | 六爻纳甲（类实现） | 结构清晰，有calculate/analyze分离 |
| `core/meihua.py` | ~250 | 梅花易数（类实现） | 结构清晰 |
| `core/qimen.py` | ~350 | 奇门遁甲（类实现） | 结构清晰 |
| `core/taiyi.py` | ~200 | 太乙神数（类实现） | 结构清晰 |

**核心问题**：5个core模块已经有类封装（`LiuYao`, `MeiHua`, `QiMen`, `TaiYi`），但**没有抽象基类**，接口不统一（有的叫`pai_pan`，有的叫`get_gua_by_number`）。

### 2.2 JS前端结构

| 文件 | 行数 | 职责 | 质量 |
|------|------|------|------|
| `engine-registry.js` | 333 | 引擎注册+调度 | **设计最好**，注册模式清晰 |
| `bazi-engine.js` | ~500 | 八字排盘+分析 | 包含完整常量定义（冗余） |
| `masters-engine.js` | ~600 | 34大师+五段式分析 | 包含完整常量定义（冗余） |
| `composite-engine.js` | ~200 | 多术合参 | getScoreFromResult分支膨胀 |
| `domain-analysis.js` | ~200 | 事域检测 | 关键词匹配，功能单一 |
| `ziwei-engine.js` | ~400 | 紫微斗数 | 包含完整常量定义（冗余） |
| 其余8个引擎 | ~200-350 | 各自术数 | 均含常量副本 |

**核心问题**：10个引擎文件各自定义 `GAN`, `ZHI`, `GAN_WUXING`, `ZHI_WUXING`, `SIXTY_JIAZI` 等基础常量，无一例外。

### 2.3 引擎模块关系

```
EngineRegistry (JS)
    ├── 注册表：10个引擎配置（key, engineName, methodName, buildParams）
    ├── 执行层：execute() → window[engineName][methodName](...args)
    └── 调度层：executeAll() → Promise.all([...])
    
CompositeEngine (JS)
    ├── 依赖 EngineRegistry.executeAll()
    ├── getScoreFromResult() → 10个引擎各有专用分支
    └── 加权融合 → 综合研判

MastersEngine (JS)
    ├── 34位大师数据（硬编码在JS中）
    ├── 五段式模板（开场/总论/专论/引用/结语）
    └── 独立于引擎注册体系
```

**核心问题**：Python端的5个引擎没有注册机制，各自独立。JS端有注册机制但Python端没有。

### 2.5 数据流

```
用户输入 → [JS前端] 引擎调度 → 前端计算 → 展示
                ↓ (可选)
         FastAPI → bazi_api.py → core/*.py → JSON响应 → 前端展示
```

**关键问题**：
- 前后端**各自独立计算**，八字排盘有两套实现
- 前端JS引擎的返回格式不统一（有的返回 `{综合运势}`, 有的返回 `{level}`, 有的返回 `{ti_yong}`）
- composite-engine.js 的 `getScoreFromResult()` 函数为每个引擎写了专用分支（switch-case），新增引擎需修改此函数

- 无请求校验中间件、无速率限制、无错误码体系

## 三、优点

1. **引擎注册模式（JS端）**：`engine-registry.js` 设计良好，新增引擎只需一条注册记录，合参代码无需改动
2. **核心算法完整**：10种术数引擎的排盘算法均已实现，数据基础扎实（1100+行常量）
3. **Python模块有类封装**：`core/` 下的5个模块已有类结构，具备升级为统一接口的基础
4. **降级设计**：`calendar.py` 对 `lunar-python` 做了优雅降级
5. **考试系统**：`test_exam.py` 有基础的算法验证框架
6. **大师体系完整**：34位大师的风格定义、五段式分析结构已成型
7. **知识库已有雏形**：`kb/`、`skills/`、`docs/masters/` 目录结构存在

## 四、问题清单

### P0 — 必须修复（阻塞工程化）

| # | 问题 | 影响 | 涉及文件 |
|---|------|------|----------|
| P0-1 | **前后端算法双重实现** | 维护成本×2，修改需同步 | `bazi-engine.js` vs `core/calendar.py`，`qimen-engine.js` vs `core/qimen.py` 等 |
| P0-2 | **常量三重冗余** | 修改一处常量需同步3+处 | `GAN_WUXING` 在 `bazi-engine.js`, `masters-engine.js`, `domain-analysis.js`, `ziwei-engine.js` 等至少5个文件中重复定义 |
| P0-3 | **无统一引擎接口** | 新增引擎无规范可循，合参需写专用分支 | 所有引擎文件，`composite-engine.js` 的 `getScoreFromResult()` |
| P0-4 | **硬编码分析模板** | 分析内容不可配置，修改需改代码 | `api/bazi_api.py` 的 `_generate_*` 函数，`masters-engine.js` 的模板 |
| P0-5 | **无配置管理** | 端口/路径等硬编码，无环境隔离 | `app.py`，全项目 |
| P0-6 | **无依赖管理** | 无法复现环境 | 无 `requirements.txt` |
| P0-7 | **单体API文件** | 532行，13个端点+分析逻辑混在一起 | `api/bazi_api.py` |

### P1 — 建议优化（影响质量）

| # | 问题 | 影响 |
|---|------|------|
| P1-1 | **无日志系统** | 线上问题无法追踪，只有 `console.warn` 和 `logger.warning` |
| P1-2 | **无结构化测试** | `test_all.py` 只是打印验证，非 pytest 体系 |
| P1-3 | **前端全局变量污染** | 所有引擎挂 `window` 对象，无命名空间隔离 |

| P1-5 | **API路由语义混乱** | 六爻/奇门等端点挂在 `/api/bazi/` 下 |

| P1-7 | **大师数据硬编码** | 34位大师数据在JS中，与 `docs/masters/` 重复 |
| P1-8 | **知识库非结构化** | `kb/` 下全是 Markdown，代码无法查询 |
