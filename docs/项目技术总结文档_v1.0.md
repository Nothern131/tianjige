## 一、项目定位

### 1.1 项目解决什么问题

天机阁是一个**中国传统术数（命理/占卜/风水）的算法化与可视化平台**，核心解决以下问题：

1. **降低术数门槛**：传统术数需要大量专业知识（天干地支、五行生克、神煞、纳甲等），普通用户无法自行排盘和解读。天机阁将复杂的排盘算法封装为自动化引擎，用户只需输入基本信息即可获得结果。

2. **统一多术数体系**：传统术数各自独立，八字、六爻、梅花、奇门、紫微等分属不同流派，天机阁将它们整合在同一平台，并提供"合参引擎"进行跨体系交叉验证。

3. **模拟大师风格**：不同命理大师（如袁天罡、邵雍、刘伯温等）有独特的分析风格和侧重点。天机阁通过"大师蒸馏引擎"模拟 34 位古今大师的断命风格，生成个性化的五段式分析。

4. **风水户型可视化**：传统风水图纸抽象难懂，天机阁提供"拼户型建造器"，支持 3×3 到 5×5 多种网格尺寸的动态户型拼接，并结合玄空飞星算法进行风水评估。

### 1.2 核心价值

| 价值维度 | 具体体现 |
|----------|----------|
| **算法完整性** | 覆盖 10 种术数体系，每种都有独立的排盘算法引擎 |
| **零 API 依赖** | 纯本地算法计算，不依赖任何外部 API 服务 |
| **大师风格化** | 34 位大师的断命风格被编码为可复用的分析模板 |
| **多引擎合参** | 跨术数体系的加权融合分析，提供更全面的视角 |
| **可视化交互** | 风水户型拼接、星空背景、动态网格等交互体验 |
| **知识体系化** | 54 个 Markdown 文档构成完整的技术与业务知识库 |

### 1.3 目标用户

- **术数爱好者**：对八字、六爻、奇门等有学习兴趣，但缺乏排盘能力
- **命理研究者**：需要多体系交叉验证的分析工具
- **风水从业者**：需要户型风水快速评估工具
- **传统文化学习者**：想了解中国传统术数算法的技术实现

### 2.3 模块间通信方式

```
                          ┌──────────────┐
                          │   用户输入    │
                          └──────┬───────┘
                                 │
              ┌──────────────────┼──────────────────┐
              │                  │                  │
              ▼                  ▼                  ▼
     ┌────────────┐    ┌────────────┐    ┌──────────────┐
     │  Hash路由   │    │  API 调用   │    │  直接引擎调用 │
     │  (app.js)  │    │  (api.js)  │    │  (registry)  │
     └─────┬──────┘    └─────┬──────┘    └──────┬───────┘
           │                 │                  │
           ▼                 ▼                  ▼
     ┌──────────┐    ┌──────────────┐   ┌──────────────┐
     │ UI 组件   │    │ Python 后端   │   │ JS 引擎       │
     │ (10个)   │    │ (FastAPI)    │   │ (10个 IIFE)  │
     └──────────┘    └──────────────┘   └──────────────┘
```

**关键通信路径**：
1. **前端纯引擎路径**：用户操作 → Hash 路由 → 引擎注册中心 → 具体 JS 引擎 → UI 组件渲染
2. **后端 API 路径**：用户操作 → api.js 发起 HTTP 请求 → FastAPI 路由 → 核心算法模块 → JSON 响应
3. **合参路径**：引擎注册中心 → 批量执行多个引擎 → 合参引擎评分融合 → 大师蒸馏引擎 → 输出
4. **静态文件**：所有 HTML/CSS/JS 通过 FastAPI 的 StaticFiles 中间件提供

### 2.4 数据流

```
用户输入（生日/时辰/问题/梦境）
    │
    ├──→ 前端 JS 引擎 ──→ 算法计算 ──→ 结果对象 ──→ UI 组件渲染
    │         │
    │         └──→ 合参引擎 ──→ 加权评分 ──→ 大师蒸馏 ──→ 五段式分析
    │
    └──→ HTTP API ──→ Python 后端 ──→ core 算法 ──→ JSON 响应 ──→ 前端渲染
```

## 三、核心技术

### 3.1 核心算法/逻辑

| 算法类别 | 具体内容 | 实现位置 |
|----------|----------|----------|
| **八字排盘** | 年柱/月柱/日柱/时柱四柱推算，基于五虎遁/五鼠遁的月干时干推算，节气判断 | core/calendar.py + static/js/bazi-engine.js |
| **十神计算** | 以日干为"我"，按五行生克+阴阳确定十神关系（比肩/劫财/食神/伤官/偏财/正财/七杀/正官/偏印/正印） | core/constants.py (SHISHEN_RELATION) + static/js/masters-engine.js (SHISHEN_MAP) |
| **旺衰判断** | 综合月令本气（权重最高）、四柱生扶、五行数量，输出旺/偏旺/中和/偏弱/弱 | static/js/masters-engine.js |
| **格局分析** | 9 种格局识别（正官格/七杀格/正印格/偏印格/食神格/伤官格/正财格/偏财格/建禄格）+ 成败条件 | static/js/masters-engine.js |
| **六爻纳甲** | 铜钱起卦 → 纳甲装卦 → 世应定位 → 六亲配属 → 六兽安布 → 动爻变化 → 变卦 → 解卦 | core/liuyao.py + static/js/liuyao-engine.js |
| **梅花易数** | 三数法/日期法起卦 → 本卦/互卦/变卦 → 体用生克 → 万物类象 → 解卦 | core/meihua.py + static/js/meihua-engine.js |
| **奇门遁甲** | 阴阳遁判断 → 局数计算 → 地盘（六仪三奇）→ 天盘（九星）→ 人盘（八门）→ 神盘（八神）→ 九宫格输出 | core/qimen.py + static/js/qimen-engine.js |
| **太乙神数** | 太乙积年 → 十六神宫位 → 五福三基 → 计神始击 → 格局判断 | core/taiyi.py + static/js/taiyi-engine.js |
| **玄空飞星** | 三元九运 → 坐山朝向 → 九宫飞泊 → 年星飞布 → 吉凶评估 | static/js/fengshui-engine.js |
| **紫微斗数** | 命宫/身宫 → 十二宫 → 四化飞星 → 主星排布 → 十干四化 | static/js/ziwei-engine.js |
| **大六壬** | 月将 → 天盘/地盘 → 四课 → 三传 → 课体判断 | static/js/daliuren-engine.js |
| **诸葛神数** | 字数法/数字法 → 签号计算 → 签诗匹配 → 解读 | api/bazi_api.py + static/js/zhuge-engine.js |
| **调候用神** | 按日干+月支查表，输出首选用神和次选用神 | core/constants.py (TIAOHOU) |
| **神煞系统** | 14 种神煞（天乙贵人/文昌/桃花/驿马/羊刃/禄神/将星/华盖/红鸾/天喜/孤辰/寡宿/劫煞/灾煞），按日干/日支/年支查表 | core/constants.py (SHENSHA) |

### 4.3 类和函数组织方式

**Python 后端**：
- 每个 `core/` 模块包含一个主类（如 `ChineseCalendar`、`LiuYao`、`MeiHua`、`QiMen`、`TaiYi`）
- 类内部按功能分组：起卦方法 → 装卦 → 分析 → 解卦
- 模块底部提供便捷函数（如 `get_full_bazi()`）作为模块级 API
- `api/bazi_api.py` 中分析生成函数以 `_generate_xxx_analysis()` 命名，均为私有函数

**JavaScript 前端**：
- 所有引擎使用 **IIFE（立即执行函数表达式）** 模式，挂载到全局 `window` 对象
- 每个引擎暴露一个主对象（如 `BaziEngine`、`LiuyaoEngine`），包含方法如 `paipan()`、`divine()`、`analyze()` 等
- UI 组件按术数类型拆分，每个组件负责特定术数的界面渲染
- `engine-registry.js` 使用注册表模式，通过 `register()`/`execute()`/`executeAll()` 统一管理

### 4.4 耦合情况分析

| 耦合点 | 描述 | 影响 |
|--------|------|------|
| **Python 后端与 JS 前端双实现** | 八字/六爻/梅花/奇门/太乙的算法在 Python 和 JS 端各有一套独立实现 | 算法变更需同步两处 |
| **api/bazi_api.py 分析函数硬编码** | `_generate_wealth_analysis()` 等函数使用硬编码的模板文本，未与 `core/constants.py` 的数据关联 | 分析模板与数据分离，但模板本身不可配置 |
| **前端引擎通过全局变量通信** | 所有 JS 引擎挂载到 `window` 对象，引擎注册中心通过 `global[config.engineName]` 动态获取 | 命名冲突风险，依赖加载顺序 |
| **UI 组件与引擎紧耦合** | 每个 `components/xxx.js` 直接依赖对应的 `xxx-engine.js` 的数据格式 | 引擎输出格式变更 → UI 组件需同步修改 |
| **大师蒸馏引擎依赖八字引擎** | `masters-engine.js` 的 `analyze()` 方法接收 `baziResult` 对象，依赖 `bazi-engine.js` 的输出格式 | 八字引擎输出格式变更 → 大师蒸馏引擎需同步修改 |
| **合参引擎依赖注册中心** | `composite-engine.js` 通过 `EngineRegistry.executeAll()` 批量执行引擎 | 引擎注册信息变更 → 合参逻辑可能受影响 |
| **api/bazi_api.py 是单一路由文件** | 所有 API 端点（八字/六爻/梅花/奇门/太乙/诸葛/大师）都在一个文件中 | 文件职责过重，530+ 行包含路由 + 模型 + 分析生成 |

## 五、数据体系

### 5.1 数据存储

| 存储方式 | 内容 | 位置 |
|----------|------|------|
| **Python 字典常量** | 所有术数基础数据（天干地支、五行、十神、神煞等） | core/constants.py |
| **JavaScript 对象常量** | 前端引擎的基础数据（与 Python 端对应） | 各 JS 引擎文件内部 |
| **Markdown 文档** | 知识库、大师档案、发布说明、使用指南 | kb/ + docs/ |
| **JSON 文件** | 考核报告数据 | exam_report.json |
| **内存对象** | 运行时状态（引擎结果、用户输入、UI 状态） | 前端 JavaScript 全局变量 |

**关键特征**：项目**不使用数据库**，所有数据均为静态常量或运行时内存对象。这带来以下特点：
- 优点：零外部依赖，部署简单（静态文件即可运行）
- 限制：无持久化能力，用户输入和结果在刷新后丢失

| **CORS 配置** | 硬编码在 `app.py` 中（allow_origins=["*"]） | app.py |
| **引擎注册信息** | `engine-registry.js` 中的 `register()` 调用 | static/js/engine-registry.js |
| **大师列表** | 硬编码在 `api/bazi_api.py` 的 `get_masters()` 中 | api/bazi_api.py |

| **分析模板文本** | 硬编码在 `api/bazi_api.py` 的 `_generate_xxx_analysis()` 函数中 | api/bazi_api.py |

**关键特征**：项目**没有独立的配置文件**（如 .env、config.yaml、settings.py），所有配置以硬编码方式分布在代码中。

### 5.4 状态保存

## 六、扩展能力分析

### 6.1 新增一个功能需要修改多少地方？

以"新增一个术数引擎（如『小六壬』）"为例：

| 步骤 | 需要修改的文件 | 数量 |

| 3. 实现 UI 组件 | 新建 `static/js/components/xiaoliuren.js` | 1 新建 |
| 4. 添加路由 | 在 `static/js/app.js` 添加 Hash 路由处理 | 1 修改 |
| 5. 添加 HTML 入口 | 在 `index.html` 添加导航链接 | 1 修改 |
| 6. 实现后端算法 | 新建 `core/xiaoliuren.py` | 1 新建 |
| 7. 添加后端 API | 在 `api/bazi_api.py` 添加路由端点和请求模型 | 1 修改 |
| 8. 添加常量数据 | 在 `core/constants.py` 添加相关常量（如有） | 1 修改 |
| 9. 更新知识库 | 在 `kb/` 添加新文档 | 1 新建 |
| **合计** | **5 新建 + 4 修改** | **9 处** |

### 6.2 新增一个角色/模块是否方便？

**新增大师**：
- 修改 `api/bazi_api.py` 的 `get_masters()` 列表
- 在 `docs/masters/` 添加大师档案
- 在 `api/bazi_api.py` 的 `_master_opening()`/`_master_overview()`/`_master_specialty()`/`_master_quote()`/`_master_closing()` 中添加对应条目
- 在 `static/js/masters-engine.js` 中添加大师风格配置
- **总计约 2 新建 + 2 修改**

**新增领域（如『子女』领域）**：
- 修改 `static/js/domain-analysis.js` 添加关键词
- 修改 `api/bazi_api.py` 添加分析函数
- **总计 2 修改**

**新增分析类型（如『健康分析』）**：
- 在 `api/bazi_api.py` 添加 `_generate_health_analysis()` 函数 + 路由端点
- 在 `static/js/masters-engine.js` 添加专项分析逻辑
- 在 `static/js/components/bazi.js` 添加 UI 展示
- **总计 3 修改**

### 6.3 哪些地方未来容易成为瓶颈？

| 瓶颈点 | 原因 | 影响 |
|--------|------|------|
| **api/bazi_api.py 文件过大** | 530+ 行包含所有路由 + 模型 + 分析生成，是单一巨石文件 | 多人协作困难，新增 API 需频繁修改同一文件 |
| **前后端算法双实现** | 八字/六爻/梅花/奇门/太乙在 Python 和 JS 端各有独立实现 | 算法变更需同步两处，容易出现不一致 |
| **分析模板硬编码** | 大师风格模板、分析文本直接硬编码在 Python 代码中 | 修改一个大师的措辞需要改代码+重新部署 |
| **无持久化存储** | 所有用户数据和计算结果在页面刷新后丢失 | 无法支持用户历史记录、偏好设置、追问上下文 |
| **全局变量通信** | 前端引擎通过 `window` 全局对象通信 | 命名冲突风险，难以追踪数据流向 |
| **无配置文件** | 所有配置项硬编码在代码中 | 部署到不同环境需要修改代码 |
| **无自动化测试** | 仅有手动测试页面（test_all_engines.html），无单元测试 | 算法变更后的回归验证依赖人工 |
| **前端无构建工具** | 原生 JS 无模块打包/压缩/转译 | 代码体积大，加载性能受限 |
| **引擎注册中心是单点** | 所有引擎的注册、调度、执行都通过 `engine-registry.js` | 注册中心故障 → 所有引擎不可用 |
| **知识库与代码分离** | Markdown 文档需要手动维护与代码的同步 | 代码变更后文档容易过时 |
